## The Problem with Traditional sRGB & HSL

In standard HSL, a pure yellow (`hsl(60, 100%, 50%)`) has the exact same lightness value as a pure blue (`hsl(240, 100%, 50%)`). Yet to human eyes, the yellow appears blindingly bright, while the blue looks deeply dark.

When building design system tokens, this discrepancy creates major headaches:

- A contrast ratio formula against white text will pass on blue but fail completely on yellow at the same 50% lightness.
- Shifting hue while attempting to keep perceived brightness requires manual tweaking and ad-hoc color adjustments.

## Why OKLCH Changes Everything

OKLCH organizes colors into three intuitive coordinates:

1. **L (Lightness):** `0%` to `100%`, directly correlating to human-perceived brightness.
2. **C (Chroma):** The saturation or purity of the color (`0` to `0.37+`).
3. **H (Hue):** The angle on the color wheel (`0deg` to `360deg`).

Because OKLCH is perceptually uniform, an `L` of `0.70` feels equally bright whether the hue is green, purple, orange, or blue.

```css
/* Radian UI primary token in OKLCH */
:root {
	--primary-50: oklch(0.97 0.02 260);
	--primary-500: oklch(0.62 0.19 260);
	--primary-900: oklch(0.24 0.08 260);
}
```

## How Radian UI Implements OKLCH

In Radian UI, all color primitives and semantic layers are calibrated using OKLCH tokens. This guarantees that whether users toggle between Light, Dark, or high-contrast Sera themes, contrast requirements (WCAG 2.1 AA) are preserved mathematically without manual color overrides.
